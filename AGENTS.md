# AGENTS.md

Guidance for AI coding agents working in this repository. (`CLAUDE.md` is a symlink to this file.)

Crossplane provider for SAP BTP: orchestrates BTP account resources (Subaccount, Entitlements, ServiceInstances, trust configs, Cloud Foundry/Kyma environments, …) as Kubernetes CRDs. Go, Crossplane v2 (`crossplane-runtime/v2`). Go 1.25 (`GO_REQUIRED_VERSION` in Makefile; the README badge saying 1.23 is stale).

## Architecture

This is a **hybrid provider with three controller implementation approaches and two code-generation pipelines**. Knowing which approach a resource uses is the single most important thing before touching it — see [`docs/contribution-notes/resource-implementation-approaches.md`](docs/contribution-notes/resource-implementation-approaches.md) (native / upjet / hybrid, and which resources use each).

### Native controllers (hand-written)
- Wired in `internal/controller/template.go` → `CustomSetup(mgr, CrossplaneOptions)`.
- Logic lives in `internal/controller/<group>/<resource>/` and talks to BTP through `internal/clients/*`, which wrap `internal/openapi_clients/*` (generated from BTP OpenAPI specs: accounts, provisioning, entitlements, service-manager, saas-provisioning, xsuaa, destination).
- Covers: subaccount, directory, entitlement, cloudfoundry, kyma, servicemanager, serviceinstance, servicebinding, subscription, rolecollection(assignment), oidc, kymaenvironmentbinding/module, destination(+certificate), etc.
- These are the resources you implement and edit by hand.

### Upjet / Terraform-backed controllers (generated)
- Wired in `internal/controller/zz_setup.go` → `Setup(mgr, UpjetOptions)`; `SetupFn` is `tfclient.TerraformSetupBuilder()`.
- Generated by upjet from the **SAP/terraform-provider-btp** schema. Per-resource external-name + config overrides live in `config/<resource>/config.go` and are registered in `config/provider.go`; `config/external_name.go` maps identifiers.
- Covers: directoryentitlement, subaccountservicebroker, trust configurations (global + subaccount), subaccountapicredential, providerconfig.
- **Never edit `zz_*.go` files or generated controllers** — change `config/` and regenerate.

`main.go` (`cmd/provider`) starts both: `template.Setup` (upjet) + `template.CustomSetup` (native). Both families also have `SetupGated` and conversion webhooks (`SetupWebhookWithManager`) — the `apis/` version packages mix hand-written and `zz_*` types with conversion hubs (v1alpha1 ↔ v1beta1), so API changes often require regen + a conversion update. A **hybrid** resource is native controller logic that delegates part of its lifecycle to an embedded upjet/Terraform client — see the approaches doc below before adding one.

## Conventions (authoritative docs)

`docs/contribution-notes/` is the ADR + pattern knowledge base ([overview](docs/contribution-notes/overview.mdx)). Read the relevant note before changing these areas; **update the note in the same PR when you change the behavior it documents** — docs and code must stay in sync.

> **Breaking changes to API contracts require explicit maintainer approval.** This covers CRD specs (`apis/`), CLI/controller flags, external-name formats, status fields consumers depend on, and any removal/rename/semantic change to a published field. Prefer additive, backward-compatible changes (new optional field, new enum value, conversion webhook). If a break is unavoidable, call it out and get sign-off before implementing — don't ship it silently.

- [resource-implementation-approaches.md](docs/contribution-notes/resource-implementation-approaches.md) — native vs upjet vs hybrid; pick before implementing a resource.
- [external-name-handling.md](docs/contribution-notes/external-name-handling.md) — external-name identifies the external resource and signals intent-to-adopt; set it from the API response in `Create()`, match on it in `Observe/Update/Delete`; **compound keys are joined with `/`**. Import flow uses `managementPolicies: Observe` + the annotation.
- [resource-usage-tracking.md](docs/contribution-notes/resource-usage-tracking.md) — cross-MR delete ordering. Every downstream controller must call `resourcetracker.Track()` in `Connect()` every reconcile; an upstream's `Delete()` consults `DeleteShouldBeBlocked`. **Never force-delete, patch finalizers, or set `deletionPolicy: Orphan` on an in-use upstream** — the BTP resource leaks.
- [caching.md](docs/contribution-notes/caching.md) — process-wide `btp.Client` cache keyed by credential bundle (`btp/cisclient.go`, singleflight-collapsed) + entitlement describe cache. Preserve the cache-key fields and singleflight when editing client construction.
- [service-binding-rotation.md](docs/contribution-notes/service-binding-rotation.md) — standardized rotation API: `.spec.rotation.{ttl,frequency}` (both required; absent = disabled), current/retired/expired instances in status. Keep the API identical across providers.
- [upgrade-tests.md](docs/contribution-notes/upgrade-tests.md) — `make upgrade-test UPGRADE_TEST_FROM_TAG=… UPGRADE_TEST_TO_TAG=… [testFilter=…]`.
- [backports.md](docs/contribution-notes/backports.md) — backport a merged PR with a `backport <branch>` label or `/backport <branch>` comment.

### CLI / controller flags
Controller flags are documented in [docs/end-user-guides/setup/configure-controller-flags.mdx](docs/end-user-guides/setup/configure-controller-flags.mdx) — keep that table in sync when adding or changing a flag.

**New flags must not be boolean.** A boolean can't evolve without a breaking change (you can't add a third state). Use an enum/string/int flag with a named default instead — e.g. `--mode=off|basic|full` rather than `--enable-x`. (The existing `--debug`, `--leader-election`, `--enable-terraform-session-reuse` booleans predate this rule; don't add more.)

### Second binary: exporter
`cmd/exporter` is a standalone CLI (built on `SAP/xp-clifford`) that logs into a BTP global account and exports existing resources as CRs. Separate from the controller; env-driven (`BTP_EXPORT_*`).

## Commands

```bash
make submodules      # FIRST, once per clone — inits the crossplane build submodule
make generate        # run BOTH codegen pipelines (see below); run after any apis/ or config/ change
make build PLATFORM=linux_amd64

# local dev loop
make dev-debug       # kind cluster + CRDs + crossplane-system ns; then debug from IDE
make dev             # run controller against the kind cluster, no debugger
make run             # run controller against current KUBECONFIG
make dev-clean       # delete the dev cluster

# quality
make lint
make test            # or: make test.run  (unit tests, = go.test.unit)
go test ./internal/clients/account/... -run TestFoo   # single unit test / package
```

`make generate` chains (see `apis/generate.go`): upjet scraper over the pinned Terraform provider docs → `cmd/generator` emits `zz_*` types/controllers from `config/schema.json` → angryjet/controller-gen for managed-resource methods → example + e2e-CR generation. The Terraform provider version is pinned in the Makefile (`TERRAFORM_PROVIDER_VERSION`); `config/schema.json` is a build-time artifact consumed by codegen.

## E2E tests (real BTP credentials required)

```bash
make test-acceptance [testFilter=<TestFuncName>]   # spins a kind cluster, runs provider as a container
make test-e2e-long   [testFilter=<TestFuncName>]   # long tests behind the `e2e_long` build tag (Kyma, binding rotation, 10min+)
```
Required env: `GLOBAL_ACCOUNT`, `CLI_SERVER_URL`, `CIS_CENTRAL_BINDING`, `BTP_TECHNICAL_USER` (see README for JSON shapes). Fixtures in `test/e2e/testdata/crs/` are `envsubst` templates — the runner renders them into gitignored `.work/rendered-crs/` and never mutates the committed templates.

## Testing conventions
- Unit tests use `crossplane-runtime` `test` helpers and table-driven cases; fakes live in `internal/clients/fakes` and `internal/testutils`.
- When mocking, patch at the import location in the module under test, not the definition site.
- Do not report work done while tests fail.

## Development workflow (workspace rule)
- **Default: one PR** carries spec (`specs/001-<feature>/spec.md`) and implementation together; keep them in sync.
- Small self-contained change (one flag, one bug fix) needs no spec — just open the PR.
- Spec-first (opt-in) only for large/risky work: spec-only PR, then stack implementation.
- Any code change that alters behavior a spec documents must update that spec in the same commit. PRs diverging from spec are blocked.
