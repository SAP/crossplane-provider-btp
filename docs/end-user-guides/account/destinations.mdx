# Manage destinations

This guide shows how to manage [SAP BTP destinations](https://help.sap.com/docs/connectivity/sap-btp-connectivity-cf/managing-destinations?locale=en-US&version=LATEST) and their client certificates in code, using the `SubaccountDestination`, `SubaccountDestinationCertificate`, and `SubaccountDestinationGeneratedCertificate` custom resources. Destinations let applications in your subaccount reach external systems (HTTP, RFC, Mail, LDAP), and destination certificates provide the client certificates some of those connections need — either uploaded by you (`SubaccountDestinationCertificate`) or generated by the Destination service (`SubaccountDestinationGeneratedCertificate`).

All three resources talk to the [Destination Service](https://help.sap.com/docs/connectivity/sap-btp-connectivity-cf/destination-service-rest-api-23ccafbea18f4b65919a2799f2cd20e6-150?locale=en-US&version=LATEST), so before you can create any of them you need a Destination service instance and a binding that hands over the OAuth2 credentials.

## 🚧 Prerequisites

- You've created a running control plane.
- You've [configured the BTP provider](../setup/configure-provider-btp.mdx).
- You've [created and set up a subaccount managed in code](./subaccount.mdx).
- You're connected to your control plane.

## Set up the Destination service

`SubaccountDestination`, `SubaccountDestinationCertificate`, and `SubaccountDestinationGeneratedCertificate` all authenticate against the Destination Service using OAuth2 credentials taken from a `Secret`. The recommended way to produce that secret is to create a Destination service instance and bind to it — the `ServiceBinding` writes the credentials into a `Secret` you then reference from your destination resources.

### Create an `Entitlement`

Entitle the `destination` service to your subaccount.

1. Save the following YAML content to `destination-entitlement.yaml`:

    ```yaml title="destination-entitlement.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: Entitlement
    metadata:
      name: destination-entitlement
    spec:
      forProvider:
        serviceName: destination
        servicePlanName: lite
        enable: true
        subaccountRef:
          name: my-subaccount
      providerConfigRef:
        name: account-provider-config
    ```

2. Apply `destination-entitlement.yaml` to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f destination-entitlement.yaml
    ```

### Create a `ServiceInstance`

Create a Destination service instance from the entitled `destination`/`lite` plan.

1. Save the following YAML content to `destination-instance.yaml`:

    ```yaml title="destination-instance.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: ServiceInstance
    metadata:
      name: destination-instance
    spec:
      forProvider:
        name: destination-instance
        serviceManagerRef:
          name: my-subaccount-service-manager
        subaccountRef:
          name: my-subaccount
        offeringName: destination
        planName: lite
      providerConfigRef:
        name: account-provider-config
    ```

    <button onClick={() => window.open("https://doc.crds.dev/github.com/SAP/crossplane-provider-btp/account.btp.sap.crossplane.io/ServiceInstance/v1alpha1@v2.1.0", "_blank")} className='button button--secondary'>See full CRD reference</button>

2. Apply `destination-instance.yaml` to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f destination-instance.yaml
    ```

### Create a `ServiceBinding`

Bind to the instance to obtain the OAuth2 credentials. The binding writes them to the `Secret` named in `spec.writeConnectionSecretToRef`. Setting `spec.forProvider.secretKey` bundles the credentials into a single JSON key (here `credentials`), which is the format the destination resources read most cleanly.

1. Save the following YAML content to `destination-binding.yaml`:

    ```yaml title="destination-binding.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: ServiceBinding
    metadata:
      name: destination-binding
    spec:
      forProvider:
        name: destination-binding
        secretKey: credentials
        serviceInstanceRef:
          name: destination-instance
        subaccountRef:
          name: my-subaccount
      writeConnectionSecretToRef:
        name: destination-binding-secret
        namespace: crossplane-system
      providerConfigRef:
        name: account-provider-config
    ```

    <button onClick={() => window.open("https://doc.crds.dev/github.com/SAP/crossplane-provider-btp/account.btp.sap.crossplane.io/ServiceBinding/v1alpha1@v2.1.0", "_blank")} className='button button--secondary'>See full CRD reference</button>

2. Apply `destination-binding.yaml` to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f destination-binding.yaml
    ```

Once the binding is ready, the `destination-binding-secret` `Secret` holds the credentials your destination resources will reference through `spec.forProvider.destinationServiceBindingSecretRef`.

:::info
The `destinationServiceBindingSecretRef` accepts two secret shapes:

- **Single JSON key** — set `key` (e.g. `credentials`), the format produced above when the `ServiceBinding` sets `secretKey`.
- **Flat keys** — leave `key` empty, and the secret must carry the individual keys `clientid`, `clientsecret`, `tokenurl` (or `token_url`), and `uri` (or `url`), the format produced when the `ServiceBinding` sets no `secretKey`.
:::

:::info
The binding must belong to the same subaccount as the resource. On every reconcile, the provider reads the subaccount the binding's access token was issued for and compares it with `spec.forProvider.subaccountId` (which `subaccountRef` or `subaccountSelector` fill in):

- **Different subaccount** — the resource goes `Synced=False` with an error naming both IDs, for example: `destination service binding belongs to subaccount <binding-subaccount-id>, but spec.forProvider.subaccountId is <subaccount-id>: point destinationServiceBindingSecretRef at a binding of subaccount <subaccount-id>`. Nothing is read or written in BTP until the binding and `spec.forProvider.subaccountId` name the same subaccount, so deleting such a resource blocks until you fix the binding or set `deletionPolicy: Orphan` (see below). This check also applies to existing `SubaccountDestination` and `SubaccountDestinationCertificate` resources after upgrading the provider.
- **Subaccount can't be verified** — if the access token carries no subaccount claim, the provider emits a `Warning` event with reason `BindingSubaccountUnverified` and carries on.
- **External name points elsewhere** — if the subaccount ID in the `crossplane.io/external-name` annotation (`<subaccount-id>/<name>`) differs from the binding's subaccount, the provider emits a `Warning` event with reason `ExternalNameSubaccountMismatch` and carries on. The binding decides where the resource lives, so correct the annotation.

Check for these warnings with `kubectl describe` on the resource. If the binding can't be fixed and you need to delete the resource anyway, set `spec.deletionPolicy: Orphan` first: the provider then lets the custom resource go without touching BTP, and you clean up the object in BTP yourself.
:::

## Create a `SubaccountDestination`

A destination stores the connection details an application uses to reach an external system. With the `SubaccountDestination` custom resource you can manage one in code. Destination-specific fields such as `URL`, `Authentication`, and `ProxyType` go into `spec.forProvider.additionalProperties` and are passed to the Destination Service as-is — see the [supported properties](https://help.sap.com/docs/connectivity/sap-btp-connectivity-cf/destination-service-rest-api-23ccafbea18f4b65919a2799f2cd20e6-150?locale=en-US&version=LATEST) for the full list.

1. Save the following YAML content to `my-destination.yaml`:

    ```yaml title="my-destination.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: SubaccountDestination
    metadata:
      name: my-destination
    spec:
      forProvider:
        name: my-destination
        type: HTTP
        additionalProperties:
          URL: https://example.com
          Authentication: NoAuthentication
          ProxyType: Internet
        subaccountRef:
          name: my-subaccount
        destinationServiceBindingSecretRef:
          name: destination-binding-secret
          namespace: crossplane-system
          key: credentials
      providerConfigRef:
        name: account-provider-config
    ```

    :::note
    `spec.forProvider.name` is the destination name in BTP and can't be changed after creation. `spec.forProvider.type` must be one of `HTTP`, `RFC`, `MAIL`, or `LDAP`.
    :::

    :::tip
    For sensitive properties you don't want in the CR spec (such as credentials for `BasicAuthentication`), put them in a `Secret` and reference it through `spec.forProvider.additionalConfigurationSecretRefs` instead of `additionalProperties`. Each referenced secret value is a JSON object that gets merged into the destination's properties.
    :::

    <button onClick={() => window.open("https://doc.crds.dev/github.com/SAP/crossplane-provider-btp/account.btp.sap.crossplane.io/SubaccountDestination/v1alpha1@v2.1.0", "_blank")} className='button button--secondary'>See full CRD reference</button>

2. Apply `my-destination.yaml` to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f my-destination.yaml
    ```

That's it! Your destination is now managed in code and visible under **Connectivity → Destinations** in the SAP BTP cockpit.

## Create a `SubaccountDestinationCertificate`

Some destinations authenticate with a client certificate. The `SubaccountDestinationCertificate` custom resource uploads and manages such a certificate. The certificate content is supplied through a `Secret` as **base64-encoded** data, and the file extension in `spec.forProvider.name` tells BTP which format the content is in.

1. Store the base64-encoded certificate content in a `Secret`. Save the following YAML content to `certificate-content-secret.yaml`:

    ```yaml title="certificate-content-secret.yaml"
    apiVersion: v1
    kind: Secret
    metadata:
      name: my-certificate-content
      namespace: crossplane-system
    type: Opaque
    stringData:
      content: <base64-encoded-certificate>
    ```

    :::note
    Replace `<base64-encoded-certificate>` with your base64-encoded certificate data, for example the output of `base64 -i my-cert.pem`.
    :::

2. Save the following YAML content to `my-certificate.yaml`:

    ```yaml title="my-certificate.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: SubaccountDestinationCertificate
    metadata:
      name: my-certificate
    spec:
      forProvider:
        # BTP determines the certificate format from the file extension in the name.
        name: my-certificate.pem
        contentSecretRef:
          name: my-certificate-content
          namespace: crossplane-system
          key: content
        subaccountRef:
          name: my-subaccount
        destinationServiceBindingSecretRef:
          name: destination-binding-secret
          namespace: crossplane-system
          key: credentials
      providerConfigRef:
        name: account-provider-config
    ```

    :::note
    The extension in `spec.forProvider.name` selects the format: `.pem`, `.cer`, `.crt` for a single X.509 certificate, or `.jks`, `.pfx`, `.p12` for a key store. Key stores (`JKS`, `PFX`, `P12`) aren't supported in FIPS environments. The name is immutable after creation.
    :::

    <button onClick={() => window.open("https://doc.crds.dev/github.com/SAP/crossplane-provider-btp/account.btp.sap.crossplane.io/SubaccountDestinationCertificate/v1alpha1@v2.2.0", "_blank")} className='button button--secondary'>See full CRD reference</button>

3. Apply both files to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f certificate-content-secret.yaml -f my-certificate.yaml
    ```

Your certificate is now managed in code and visible under **Connectivity → Certificates** in the SAP BTP cockpit.

## Create a `SubaccountDestinationGeneratedCertificate`

Instead of uploading a certificate you obtained elsewhere, you can let the Destination service generate one for you. The `SubaccountDestinationGeneratedCertificate` custom resource asks the Destination service to create a key pair and a client certificate issued by SAP Cloud PKI, stored in the subaccount certificate store. The key pair is created in BTP, so you never handle the private key, and with `automaticRenew` the Destination service renews the certificate before it expires, keeping its name, password, and type.

Use `SubaccountDestinationGeneratedCertificate` when the target system trusts SAP Cloud PKI and you want BTP to own the key and the renewal. Use `SubaccountDestinationCertificate` when you need to bring your own certificate, for example one issued by your company CA.

The file extension in `spec.forProvider.name` selects the format: `.p12` for a PKCS#12 key store, or `.pem` for a private key with its certificate chain. All other fields are optional: if you leave out `commonName` or `validity`, the Destination service applies its defaults, and if you leave out `passwordSecretRef`, the private key or key store isn't password-protected, the same as when you generate a certificate in the cockpit.

### Generate a `.p12` key store

1. Store the key store password in a `Secret`. Save the following YAML content to `generated-certificate-password.yaml`:

    ```yaml title="generated-certificate-password.yaml"
    apiVersion: v1
    kind: Secret
    metadata:
      name: my-generated-certificate-password
      namespace: crossplane-system
    type: Opaque
    stringData:
      password: <keystore-password>
    ```

    :::note
    The provider reads the password only when it generates the certificate. Changing the `Secret` afterwards doesn't change the password of the existing key store.
    :::

2. Save the following YAML content to `my-generated-certificate.yaml`:

    ```yaml title="my-generated-certificate.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: SubaccountDestinationGeneratedCertificate
    metadata:
      name: my-generated-certificate
    spec:
      forProvider:
        # The extension selects the format: .p12 (key store) or .pem.
        name: my-generated-certificate.p12
        commonName: my-app-client
        validity:
          timeUnit: MONTHS
          value: 6
        automaticRenew: true
        passwordSecretRef:
          name: my-generated-certificate-password
          namespace: crossplane-system
          key: password
        subaccountRef:
          name: my-subaccount
        destinationServiceBindingSecretRef:
          name: destination-binding-secret
          namespace: crossplane-system
          key: credentials
      providerConfigRef:
        name: account-provider-config
    ```

    :::note
    `commonName` must be 1 to 64 characters long. `validity.timeUnit` is one of `DAYS`, `MONTHS`, or `YEARS`, and `validity.value` must be at least `1`; the Destination service rejects values above the SAP Cloud PKI maximum. `automaticRenew` defaults to `false`.
    :::

3. Apply both files to your control plane:

    ```sh title="Run in terminal"
    kubectl create -f generated-certificate-password.yaml -f my-generated-certificate.yaml
    ```

### Generate a `.pem` certificate

The minimal manifest needs the name, a subaccount reference, and the binding reference. The Destination service picks the common name and the validity, and the private key isn't password-protected:

```yaml title="my-generated-pem.yaml"
apiVersion: account.btp.sap.crossplane.io/v1alpha1
kind: SubaccountDestinationGeneratedCertificate
metadata:
  name: my-generated-pem
spec:
  forProvider:
    name: my-generated-pem.pem
    subaccountRef:
      name: my-subaccount
    destinationServiceBindingSecretRef:
      name: destination-binding-secret
      namespace: crossplane-system
      key: credentials
  providerConfigRef:
    name: account-provider-config
```

### Check the certificate

Once the certificate is generated, the provider reports the public data of the leaf certificate in `status.atProvider.certificate`: `subject`, `commonName`, `issuer`, `serialNumber`, `notBefore`, `notAfter`, and `sha256Fingerprint`. The private key and the password are never reported. `kubectl get` shows the common name and the expiry date:

```sh title="Run in terminal"
kubectl get subaccountdestinationgeneratedcertificates
```

```text
NAME                       SYNCED   READY   CN              NOT-AFTER              EXTERNAL-NAME                                                       AGE
my-generated-certificate   True     True    my-app-client   2027-05-05T09:12:44Z   6f0e5c1a-0000-4c1e-9d6b-2a1b3c4d5e6f/my-generated-certificate.p12   3m
```

When the Destination service renews the certificate, `notAfter` moves forward and `serialNumber` changes. Once `notAfter` has passed, the resource goes `Ready=False` with the message `certificate expired at <notAfter>`.

### Rotate a generated certificate

The CRD rejects adding, changing, or removing `name`, `commonName`, `validity`, `automaticRenew`, or `passwordSecretRef` once the resource exists, and the provider never regenerates a certificate in place. `destinationServiceBindingSecretRef` and the subaccount fields stay mutable, so you can switch to another binding of the same subaccount. Don't point a resource at another subaccount: the provider would generate a new certificate there and leave the old one behind, still renewing. To rotate a certificate:

1. Create a second `SubaccountDestinationGeneratedCertificate` with a new `spec.forProvider.name`.
2. Point the destinations that use the certificate at the new name.
3. Delete the old `SubaccountDestinationGeneratedCertificate`.

### Use the certificate in a destination

Reference the generated certificate from a `SubaccountDestination` with `ClientCertificateAuthentication`: set `KeyStoreLocation` to the certificate name in `additionalProperties`, and pass `KeyStorePassword` through a `Secret` referenced from `additionalConfigurationSecretRefs`, so the password stays out of the CR spec.

```yaml title="my-mtls-destination.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: my-mtls-destination-properties
  namespace: crossplane-system
type: Opaque
stringData:
  properties: |
    {"KeyStorePassword": "<keystore-password>"}
---
apiVersion: account.btp.sap.crossplane.io/v1alpha1
kind: SubaccountDestination
metadata:
  name: my-mtls-destination
spec:
  forProvider:
    name: my-mtls-destination
    type: HTTP
    additionalProperties:
      URL: https://example.com
      Authentication: ClientCertificateAuthentication
      ProxyType: Internet
      KeyStoreLocation: my-generated-certificate.p12
    additionalConfigurationSecretRefs:
      - name: my-mtls-destination-properties
        namespace: crossplane-system
        key: properties
    subaccountRef:
      name: my-subaccount
    destinationServiceBindingSecretRef:
      name: destination-binding-secret
      namespace: crossplane-system
      key: credentials
  providerConfigRef:
    name: account-provider-config
```

### Limitations

:::caution
- **No revocation.** SAP Cloud PKI doesn't revoke certificates. After you delete a generated certificate, or after it's renewed, the old certificate stays valid until it expires.
- **FIPS.** `.p12` key stores aren't supported in environments based on FIPS (Federal Information Processing Standard, the US government standard for cryptography).
- **Lost auto-renew isn't detected.** The Destination Service REST API can't tell a generated certificate from an uploaded one, and doesn't return the auto-renew or validity settings. If the certificate is changed outside Crossplane, for example re-uploaded in the cockpit, auto-renew is lost and the provider won't notice.
:::

## ⁉ FAQs

### How do I adopt a destination or certificate that already exists in BTP?

All three resources use a compound external-name in the form `<subaccount-id>/<name>`. Set the `crossplane.io/external-name` annotation to that value on your manifest so the provider adopts the existing object instead of creating a new one. See [External name](../import-landscape/external-name.md#subaccountdestination) for the exact format and how to find the IDs in the cockpit or via the API ([SubaccountDestinationCertificate](../import-landscape/external-name.md#subaccountdestinationcertificate), [SubaccountDestinationGeneratedCertificate](../import-landscape/external-name.md#subaccountdestinationgeneratedcertificate)).

To adopt a certificate that was generated by the Destination service, use `SubaccountDestinationGeneratedCertificate`. The provider can't read the generation settings back from BTP, so it doesn't compare `commonName`, `validity`, `automaticRenew`, or `passwordSecretRef` with the adopted certificate; it only reports what it observes in `status.atProvider.certificate`.

:::warning
Don't adopt a generated certificate into `SubaccountDestinationCertificate`. That resource uploads the content from its `contentSecretRef`, which turns the certificate into an uploaded one and drops auto-renew.
:::

### Where do the OAuth2 credentials in `destinationServiceBindingSecretRef` come from?

They come from a binding to a Destination service instance — the `ServiceBinding` created in [Set up the Destination service](#set-up-the-destination-service) writes them into a `Secret`. You can also create that secret manually as long as it matches one of the two accepted formats described in the info box above.

### Why doesn't my `spec.forProvider.name` change take effect?

The destination and certificate names are immutable — the CRD rejects changes to `spec.forProvider.name` once the resource is created. To rename, delete the resource and create a new one with the new name.
