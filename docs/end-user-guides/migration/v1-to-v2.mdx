# Migrate the BTP provider from v1.x to v2.0.0

Provider v2.0.0 removes two legacy concepts ([External Secret Stores](#step-2-move-off-external-secret-stores-ess) and [`GlobalAccount`](#step-3-set-the-global-account-in-providerconfig-drop-globalaccount-refs)) and moves to the Crossplane v2 runtime. Managed resources stay cluster-scoped, so most manifests are unchanged.

## Do I need to upgrade Crossplane core?

**No.** Provider v2.0.0 runs on both Crossplane [v1](https://docs.crossplane.io/v1.20/) and [v2](https://docs.crossplane.io/v2.4/) control planes. Adopting it is independent of your Crossplane version - you can install it without upgrading Crossplane, and upgrade Crossplane on its own schedule.

## Step 1: run the pre-upgrade check

Run this while the **v1.x provider is still installed**. It is read-only - it detects the four migration conditions and prints which of the steps below apply to you. It mutates nothing.

```sh
#!/usr/bin/env bash
# crossplane-provider-btp v1.x -> v2.0.0 pre-upgrade check. Read-only.
# Usage: ./btp-v2-preupgrade-check.sh
# Requires: kubectl pointed at the cluster running the v1.x provider (via KUBECONFIG or current context).
set -uo pipefail

btp_ga=globalaccounts.account.btp.sap.crossplane.io
btp_sc=storeconfigs.btp.sap.crossplane.io
found=0
note() { printf '\n[FOUND] %s\n' "$1"; found=1; }
ok()   { printf '[ok]    %s\n' "$1"; }

# 1. External Secret Stores (ESS)
check_ess() {
  local ess pub
  ess=$( { kubectl get storeconfigs.secrets.crossplane.io -A -o name 2>/dev/null; \
           kubectl get "$btp_sc" -A -o name 2>/dev/null; } | sort -u )
  # MRs that publish connection details: print kind/name<TAB>target, keep rows with a target set.
  pub=$(kubectl get managed -A \
        -o jsonpath='{range .items[*]}{.kind}/{.metadata.name}{"\t"}{.spec.publishConnectionDetailsTo.name}{"\n"}{end}' 2>/dev/null \
        | awk -F'\t' 'NF==2 && $2!=""')
  if [[ -n $ess || -n $pub ]]; then
    note "ESS in use -> do step 2. Publishing stops silently on v2.0.0 (highest impact)."
    [[ -n $ess ]] && printf '  StoreConfigs:\n%s\n' "$ess"
    [[ -n $pub ]] && printf '  Resources publishing connection details (resource -> target):\n%s\n' "$pub"
  else
    ok "No ESS StoreConfigs or publishConnectionDetailsTo usage."
  fi
}

# 2. GlobalAccount CRs / refs
check_globalaccount() {
  local ga refs
  ga=$(kubectl get "$btp_ga" -A -o name 2>/dev/null)
  # Subaccounts still carrying a ref/selector: print name<TAB>ref<TAB>selector, keep rows with either set.
  # Subaccount is cluster-scoped, so there is no namespace to print.
  refs=$(kubectl get subaccounts.account.btp.sap.crossplane.io \
         -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.forProvider.globalAccountRef}{"\t"}{.spec.forProvider.globalAccountSelector}{"\n"}{end}' 2>/dev/null \
         | awk -F'\t' 'NF==3 && ($2!="" || $3!="") {print $1}')
  if [[ -n $ga || -n $refs ]]; then
    note "GlobalAccount CRs or refs present -> do step 3. CR is removed in v2.0.0."
    [[ -n $ga ]] && printf '  GlobalAccount CRs:\n%s\n' "$ga"
    [[ -n $refs ]] && printf '  Subaccount(s) still carrying globalAccountRef/Selector (cosmetic, unread):\n%s\n' "$refs"
  else
    ok "No GlobalAccount CRs or refs."
  fi
}

# 3. ServiceManager planName default flip
check_servicemanager() {
  local sm soa
  # ServiceManager is cluster-scoped, so there is no namespace to print.
  sm=$(kubectl get servicemanagers.account.btp.sap.crossplane.io \
        -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.forProvider.planName}{"\n"}{end}' 2>/dev/null)
  soa=$(printf '%s\n' "$sm" | grep -w 'service-operator-access')
  if [[ -n $soa ]]; then
    note "ServiceManager(s) on service-operator-access -> do step 4. Default flips to subaccount-admin."
    printf '%s\n' "$soa"
  else
    ok "No ServiceManager relies on service-operator-access."
  fi
}

summary() {
  echo
  if [[ $found -eq 0 ]]; then
    echo "== Clear. Nothing btp-specific blocks the v2.0.0 upgrade. =="
  else
    echo "== Action needed: run the flagged steps below, then upgrade. =="
  fi
}

echo "== crossplane-provider-btp v2.0.0 pre-upgrade check =="
check_ess
check_globalaccount
check_servicemanager
summary
```

Each `[FOUND]` line names the step to run. If every line is `[ok]`, skip to [After you upgrade](#after-you-upgrade). Do the flagged steps while the **v1.x provider is still running**.

## Step 2: move off External Secret Stores (ESS)

Do this if the check reported **ESS in use**.

v2.0.0 removes the ESS code path. Publishing via `publishConnectionDetailsTo` stops the moment you install v2.0.0 - on any core version, with no error.

Switch each flagged resource to a native connection secret via `spec.writeConnectionSecretToRef`, or use the [External Secrets Operator](https://external-secrets.io/), before upgrading. Upstream detail: [Crossplane upgrade-to-v2, External Secret Stores](https://docs.crossplane.io/latest/guides/upgrade-to-crossplane-v2/#external-secret-stores).

The provider also removes its own `StoreConfig` CRD (`storeconfigs.btp.sap.crossplane.io`). Delete any provider `StoreConfig` while the v1.x controller still runs:

```sh
kubectl delete storeconfigs.btp.sap.crossplane.io --all
```

Any `StoreConfig` left behind is orphaned after the upgrade - see [After you upgrade](#after-you-upgrade) for CRD cleanup.

## Step 3: set the global account in `ProviderConfig`, drop `GlobalAccount` refs

Do this if the check reported **GlobalAccount CRs or refs present**.

The `GlobalAccount` managed resource is removed. If `ProviderConfig.spec.globalAccount` is not set yet, set it to your global account subdomain (see [Configure the provider](../setup/configure-provider-btp.mdx)):

```yaml
apiVersion: btp.sap.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: default
spec:
  globalAccount: <your-global-account-subdomain>
```

Then remove `spec.forProvider.globalAccountRef` / `globalAccountSelector` from the flagged `Subaccount`s - they reference the removed CR. This is cosmetic: the ref only ever wrote `globalAccountGuid`, which no controller reads. The global account comes from the SAP Cloud Management service binding (`cisCredentials`), so removing the ref changes no behaviour.

Delete the `GlobalAccount` CRs while the v1.x controller still runs, so it clears finalizers cleanly:

```sh
kubectl delete globalaccounts.account.btp.sap.crossplane.io --all
```

## Step 4: pin `planName` on ServiceManager

Do this if the check reported **ServiceManager(s) on service-operator-access**.

v2.0.0 changes the default `ServiceManager` `spec.forProvider.planName` from `service-operator-access` to `subaccount-admin`. `service-operator-access` is for the [SAP BTP Service Operator](https://github.com/SAP/sap-btp-service-operator/blob/main/README.md); `subaccount-admin` is the general-purpose plan for direct API access.

Existing resources are safe: the default applies only at create time, then persists, and `planName` is immutable. The one risk is a fresh create or GitOps recreate that omits `planName` - the CRD default now fills it with `subaccount-admin`.

Pin the plan on the flagged resources - a no-op for running ones, and it makes GitOps re-creates deterministic:

```yaml
spec:
  forProvider:
    planName: service-operator-access
```

## After you upgrade

Upgrade succeeds either way and **no BTP-side data is lost**. If the check flagged step 2 or step 3, clean up the removed CRDs now - Crossplane does **not** GC them (`globalaccounts` and, if you used ESS, `storeconfigs.btp.sap.crossplane.io`). The steps differ by Crossplane version; repeat them for each removed CRD.

### Crossplane v1

```sh
kubectl delete globalaccounts.account.btp.sap.crossplane.io --all
kubectl delete crd globalaccounts.account.btp.sap.crossplane.io
kubectl delete storeconfigs.btp.sap.crossplane.io --all
kubectl delete crd storeconfigs.btp.sap.crossplane.io
```

Delete the CRs first - the CRD's `customresourcecleanup` finalizer holds it in `Terminating` until they are gone.

### Crossplane v2

The CRD is owned by a `ManagedResourceDefinition` (MRD) that re-creates it on every reconcile, so `kubectl delete crd` alone is a no-op. Delete the MRD first:

```sh
kubectl delete globalaccounts.account.btp.sap.crossplane.io --all
kubectl delete managedresourcedefinition.apiextensions.crossplane.io globalaccounts.account.btp.sap.crossplane.io
kubectl delete crd globalaccounts.account.btp.sap.crossplane.io
kubectl delete storeconfigs.btp.sap.crossplane.io --all
kubectl delete managedresourcedefinition.apiextensions.crossplane.io storeconfigs.btp.sap.crossplane.io
kubectl delete crd storeconfigs.btp.sap.crossplane.io
```

## If you skip the steps

- **ESS (2)** - connection details stop being published. Consumers reading that secret (workloads, other resources, GitOps) get stale or missing credentials. No error is raised, so the break is easy to miss. Highest impact.
- **Refs (3)** - cosmetic only. A leftover `globalAccountRef` / `globalAccountSelector` is an unknown field on the v2 CRD; it is not read, so nothing breaks.
- **planName (4)** - existing ServiceManagers are unaffected. Only a fresh create or GitOps recreate that omits `planName` adopts the new `subaccount-admin` default; if it backed the SAP BTP Service Operator, fixing the plan needs a delete + recreate (immutable). Lowest impact of the four.
- **Cleanup (after upgrade)** - orphaned CRs and the removed CRDs (`globalaccounts`, `storeconfigs.btp.sap.crossplane.io`) linger until removed manually (on core v2 also their `ManagedResourceDefinition`).
