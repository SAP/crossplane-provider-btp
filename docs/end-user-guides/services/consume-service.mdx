# Consume services

This guide shows how to consume service instances from external tools such as other Crossplane providers. As an example, we'll use the [Crossplane HANA Provider](/docs/crossplane-provider-hana/docs/end-user-guides/hana) to orchestrate a database schema inside the newly created SAP HANA Cloud service instance.

:::image-light
![Big picture](/img/overview-orchestrate-service-all.png)
:::

## 🚧 Prerequisites

- You've [created and set up a subaccount managed in code](/docs/crossplane-provider-btp/docs/end-user-guides/account/subaccount).
- You've [created an `Entitlement` and a `ServiceInstance` for the SAP HANA Cloud service](/docs/crossplane-provider-btp/docs/end-user-guides/services/create-services).

## Create a `ServiceBinding`

A service binding on SAP BTP contains credentials to access a service instance. You can create such a service binding with the `ServiceBinding` custom resource.
The credentials are stored in a `Secret` you specify via `spec.writeConnectionSecretToRef`.

1. Save the following YAML content as `hana-binding.yaml`:

    ```yaml title="hana-binding.yaml"
    apiVersion: account.btp.sap.crossplane.io/v1alpha1
    kind: ServiceBinding
    metadata:
      name: hana-binding
    spec:
      forProvider:
        name: hana-binding
        serviceInstanceRef:
          name: hana-cloud-instance
        subaccountRef:
          name: my-subaccount
      writeConnectionSecretToRef:
        name: hana-binding-secret
        namespace: default
      providerConfigRef:
        name: account-provider-config
    ```

    <button onClick={() => window.open("https://doc.crds.dev/github.com/SAP/crossplane-provider-btp/account.btp.sap.crossplane.io/ServiceBinding/v1alpha1@v1.6.0", "_blank")} className='button button--secondary'>See full CRD reference</button>

2. Apply `hana-binding.yaml` to your managed control plane:

    ```sh title="Run in terminal"
    kubectl apply -f hana-binding.yaml
    ```

## ⁉ FAQs

### Why does re-applying my `ServiceBinding` fail with a conflict on `spec.rotation`?

If you enable credential rotation via `spec.rotation` with shorthand durations, applying the very same manifest a second time fails:

```text
Apply failed with 2 conflicts: conflicts with "crossplane-provider-btp" using account.btp.sap.crossplane.io/v1alpha1:
- .spec.rotation.frequency
- .spec.rotation.ttl
```

The provider rewrites duration values into the canonical Go form that spells out every unit down to seconds — `720h` becomes `720h0m0s` — and becomes the field manager of those fields while doing so. Your next server-side apply (`kubectl apply --server-side`, Helm, Flux, Argo CD) still sends `720h`, so the API server sees a competing value and reports a conflict. Any other duration field in a resource spec, such as a `KymaEnvironmentBinding`'s `spec.forProvider.rotationInterval` and `spec.forProvider.ttl`, can be rewritten the same way.

Write durations in canonical form from the start:

```yaml title="hana-binding.yaml"
spec:
  rotation:
    frequency: 720h0m0s # 30 days
    ttl: 1080h0m0s # 45 days
```

If you already hit the conflict, changing the manifest to the canonical form resolves it — no need to force-apply or delete the resource.
