# Authenticate the provider

This page describes how to authenticate the Crossplane BTP provider.

:::image-light
![BTP provider authentication overview: combine a central CIS service binding with IAS trusted OIDC (recommended) or technical-user credentials (development only).](/img/btp-auth.png)
:::


It requires **a central SAP Cloud Management service (CIS) instance** binding created _(manually or via CLI/API)_ in a subaccount belonging to the global account where you want to orchestrate your resources.

as well as

a **Passwordless ServiceAccount** trusted by IAS or a static technical user.

:::warning Avoid static users

A technical user with static credentials is the simpler option to setup.
For production, however, we strongly recommend IAS trusted OIDC to avoid storing a long-lived user password.

:::

The diagrams below show the shared manual subaccount containing the central CIS
instance and service binding. Once authenticated, the provider can orchestrate
other subaccounts and their resources in the same global account.

<Tabs groupId="btp-authentication" defaultValue="technical-user">
  <TabItem value="technical-user" label="Technical user">

The provider uses the CIS binding Secret and a separate Secret containing the
technical user's static credentials.

:::image-light
![Technical-user authentication: a manual subaccount provides the central CIS binding, and the BTP provider uses static user credentials to orchestrate resources in the global account.](/img/authenticate-btp-static.png)
:::

  </TabItem>
  <TabItem value="ias-oidc" label="IAS trusted OIDC">

The provider uses the CIS binding Secret and IAS trusts the control plane's
OIDC issuer. It maps the provider's projected ServiceAccount token to a
passwordless workload user with BTP role assignments.

:::image-light
![IAS trusted OIDC authentication: the global account trusts IAS, and the BTP provider uses a projected ServiceAccount token alongside the central CIS binding to orchestrate resources.](/img/authenticate-btp-oidc.png)
:::

  </TabItem>
</Tabs>

##  🚧 Prerequisites

- An existing [global account](https://discovery-center.cloud.sap/card/3bfb0ce5-46e2-428f-b3be-5d4482322b55) on SAP BTP
- [BTP provider installed on a control plane](./install-provider-btp.mdx)

## Set up SAP Cloud Management service

To orchestrate your global account, you need one instance of the SAP Cloud Management service (with the **`central`** plan) in one of your subaccounts.
To enable API access to the service instance, you need a **service binding**.

The following steps create a `client_credentials` binding, which is supported by both approaches.

<Tabs>
  <TabItem value="bpt-cli" label="Using the btp CLI">

    :::note Install the btp CLI

    If you haven't installed the BTP Command Line Interface (btp CLI) yet, follow the guide from the SAP Developer Center: [Get Started with the SAP BTP Command Line Interface (btp CLI)](https://developers.sap.com/tutorials/cp-sapcp-getstarted.html).

    :::

		To create a subaccount containing an instance and binding of the Cloud Management service, complete the following steps:

    1. Log in to the CLI using SSO:

        ```sh title="Run in Terminal"
        btp login --sso
        ```

    2. Create a new subaccount:

        ```sh title="Run in Terminal" {1}
        btp create accounts/subaccount --display-name "cloud-management-subaccount" --region <region> --subdomain <subaccount-subdomain>
        ```

        Replace the following:

        - `<region>`: The region in which to create the subaccount
        - `<subaccount-subdomain>`: The subdomain of the subaccount. Must be unique within the defined region <br/><br/>

        <details>
					<summary> View available regions </summary>

					Run the following command to see available regions.

					```shell title="Run in Terminal" {1}
						btp list accounts/available-region --global-account <global-account-subdomain>
					```

        </details>

    3. Copy the subaccount ID to the clipboard.

    4. Create an SAP Cloud Management service entitlement, instance, and binding by running the commands below.

        ```sh title="Run in Terminal" {1}
        export BTP_SUBACCOUNT_ID=<subaccount-id>
        # Create a service entitlement
        btp assign accounts/entitlement --for-service cis --plan central --enable true --to-subaccount $BTP_SUBACCOUNT_ID
        sleep 5
        # Create a service instance
        btp create services/instance --offering-name cis --service my-cis --plan-name central --parameters '{"grantType": "clientCredentials"}' --subaccount $BTP_SUBACCOUNT_ID
        # Create a service binding
        btp create services/binding --name my-cis-binding --instance-name my-cis --subaccount $BTP_SUBACCOUNT_ID
        btp get services/binding --name  my-cis-binding --subaccount $BTP_SUBACCOUNT_ID
        ```

        Replace `<subaccount-id>` with the ID of your newly created subaccount.

    5. From the output of the previous commands, copy the binding credentials to your clipboard. You'll need the credentials to create a Kubernetes secret.
  </TabItem>

#### Create `Secret`: CIS

For **both authentication approaches**, create a Kubernetes Secret containing the
service binding credentials. Both `ProviderConfig` examples below reference this
same `cis-provider-secret`, using namespace `default` and key `data`.

<Tabs>
  <TabItem value="programmatically" label="Using the CLI">

    :::note Install `jq`

    You need [`jq`](https://jqlang.github.io/jq/) installed to create a `Secret` using only the CLI.

    :::

    To create a `Secret`, run the commands below.

    ```sh title="Run in Terminal":
    btp --format json get services/binding --name my-cis-binding --subaccount $BTP_SUBACCOUNT_ID  | jq .credentials -r > binding.json
    kubectl create secret generic cis-provider-secret -n default --from-file=data=./binding.json -o json
    ```
  </TabItem>
  <TabItem value="manually" label="Manually">
 1. Copy the following YAML content and replace the value of `stringData.data` with the credentials from your SAP Cloud Management service binding.

      - If you followed the steps in [Set up SAP Cloud Management service](#set-up-sap-cloud-management-service), the binding credentials should already be copied to your clipboard.<br/>
      <br/>

      ```yaml title="examples/provider/cis-provider-secret.yaml" {9-41}
      apiVersion: v1
      kind: Secret
      metadata:
          namespace: default
          name: cis-provider-secret
      type: Opaque
      stringData:
          data: |
              {
                "endpoints": {
                  "accounts_service_url": "...",
                  "cloud_automation_url": "...",
                  "entitlements_service_url": "...",
                  "events_service_url": "...",
                  "external_provider_registry_url": "...",
                  "metadata_service_url": "...",
                  "order_processing_url": "...",
                  "provisioning_service_url": "...",
                  "saas_registry_service_url": "..."
                },
                "grant_type": "client_credentials",
                "sap.cloud.service": "com.sap.core.commercial.service.central",
                "uaa": {
                  "apiurl": "...",
                  "clientid": "...",
                  "clientsecret": "...",
                  "credential-type": "binding-secret",
                  "identityzone": "...",
                  "identityzoneid": "...",
                  "sburl": "...",
                  "subaccountid": "...",
                  "tenantid": "...",
                  "tenantmode": "shared",
                  "uaadomain": "...",
                  "url": "...",
                  "verificationkey": "...",
                  "xsappname": "...",
                  "xsmasterappname": "...",
                  "zoneid": "..."
                }
              }
      ```

2. Save the updated YAML content to `cis-provider-secret.yaml`.

3. Apply the secret to your control plane:

    ```sh title="Run in Terminal"
    kubectl apply -f cis-provider-secret.yaml
    ```

## Set up authentication

Choose one approach. The selection is shared with the `ProviderConfig` tabs below.

<Tabs groupId="btp-authentication" defaultValue="technical-user">
  <TabItem value="technical-user" label="Technical user">

#### Create a technical user

To allow Crossplane to communicate with the BTP API, we also need a technical user to be created on BTP.
It's important that this technical user has admin rights to the subaccount so that Crossplane can be able to create and manage resources.

A technical user is a non-human user account created specifically for programmatic access to systems, services, or applications. Unlike regular user accounts, technical users are intended to be used by automated processes and tools rather than individuals.
They are typically granted specific permissions tailored to the tasks they need to perform. It's a good practice to use a technical user for configuring the BTP subaccount instead of individual IDs.

#### Validate the technical user

1. Once the technical user is created, please add it to the global account and the subaccount with admin privilege as described in the SAP Help Portal: [Assign User Groups to Role Collections](https://help.sap.com/docs/btp/sap-business-technology-platform/assign-user-groups-to-role-collections?locale=en-US&version=LATEST).

    ```sh
    btp assign security/role-collection "Global Account Administrator" \
      --to-user <technical-user-email> \
      --create-user-if-missing true \
      --global-account <global-account-subdomain>

    btp assign security/role-collection "Subaccount Administrator" \
      --to-user <technical-user-email> \
      --create-user-if-missing true \
      --subaccount <cloud-management-subaccount-id>
    ```

    Replace the following:
    - `<technical-user-email>`: The email of the technical user
    - `<global-account-subdomain>`: The subdomain of the global account. To be found in the BTP cockpit in the **Account
      Overview** of the global account under heading **Global Account: ...** or under **Switch Global Account**
    - `<cloud-management-subaccount-id>`: The ID of the `cloud-management-subaccount` you created previously

2. Log in to the SAP BTP cockpit using the technical user in an incognito browser window of your choice, ensuring that SSO is disabled.
3. Verify that the technical user can authenticate with the BTP through the btp CLI:

    ```sh title="Run in Terminal" {1}
    btp login --url <btp-environment-url> --user <technical-user-email> --password <technical-user-password> --subdomain <global-account-subdomain>
    ```

    Replace the following:
    - `<btp-environment-url>`: The CLI server URL
    - `<technical-user-email>`: The email of the technical user
    - `<technical-user-password>`: The password of the technical user
    - ` <global-account-subdomain>`: The subdomain of the global account. To be found in the BTP cockpit in the **Account
      Overview** of the global account under heading **Global Account: ...** or under **Switch Global Account**


####  Create `Secret`: technical user

You can create a `Secret` using the technical user _(P-user)_ credentials.

1. Save the following YAML content to `sa-provider-secret.yaml`.

    ```yaml title="sa-provider-secret.yaml" {10-12}
    apiVersion: v1
    kind: Secret
    metadata:
        namespace: default
        name: sa-provider-secret
    type: Opaque
    stringData:
        credentials: |
            {
              "email": "<technical-user-email>",
              "username": "<technical-user-username>",
              "password": "<technical-user-password>"
            }
    ```

    Replace the following:

    - `<technical-user-email>`: The email address of the technical user
    - `<technical-user-username>`: The username of the technical user
    - `<technical-user-password>`: The password of the technical user

    :::note Differences in BTP landscapes

    We noticed that for some BTP landscapes (cn40) the `<technical-user-username>` does not work (resulting in 401 errors when trying to reconciliate e.g. ServiceManager). In this case, the `<technical-user-username>` must be set with the email address of the technical user too.

    :::

2. Apply `sa-provider-secret.yaml` to your control plane:

    ```sh title="Run in Terminal" {1}
    kubectl apply -f sa-provider-secret.yaml
    ```

  </TabItem>
  <TabItem value="ias-oidc" label="IAS trusted OIDC">

You will create a passwordless IAS user, trust the control plane's tokens, grant
the user BTP permissions, and mount a token into the provider.

This guide uses **OIDC workload identity for CLI/Cloud Foundry authentication**
and the existing **`client_credentials` CIS binding for direct CIS API calls**.
Those CIS calls use the service client's permissions, not the workload user's
BTP roles. No additional IAS consumer application or API dependency is needed.

#### OIDC setup

##### Issuer URL

IAS uses the control plane's **ServiceAccount issuer URL** to verify the provider's
projected token.

On the **provider's control plane**, save the following as `runtime-config.yaml`.
Replace `IAS_ISSUER`, the ServiceAccount name and `WORKLOAD_IDENTITY_VERSION` with
your own values. The ServiceAccount must match the NameID mapping above.

```yaml title="runtime-config.yaml"
apiVersion: pkg.crossplane.io/v1beta1
kind: DeploymentRuntimeConfig
metadata:
  name: provider-btp-workload
spec:
  serviceAccountTemplate:
    metadata:
      name: provider-btp
  deploymentTemplate:
    spec:
      selector: {}
      template:
        spec:
          containers:
            - name: package-runtime
              volumeMounts:
                - name: workload-assertion
                  mountPath: /var/run/secrets/workload
                  readOnly: true
          volumes:
            - name: workload-assertion
              projected:
                sources:
                  - serviceAccountToken:
                      audience: IAS_ISSUER
                      expirationSeconds: 600
                      path: token
---
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-btp
spec:
  package: ghcr.io/sap/crossplane-provider-btp/crossplane/provider-btp:WORKLOAD_IDENTITY_VERSION
  runtimeConfigRef:
    name: provider-btp-workload
```

Preserve existing runtime settings and the Kubernetes API token when adapting
your installation. Mount the additional token's directory without `subPath` so
rotation remains visible. For an operator-managed installation, update its owning
configuration rather than overwriting generated resources.

kubectl apply -f runtime-config.yaml

## Create `ProviderConfig`

We now have everything in place to create the `ProviderConfig`.

<Tabs groupId="btp-authentication" defaultValue="technical-user">
  <TabItem value="technical-user" label="Technical user">

Reference the CIS binding Secret and the technical-user credentials Secret.

```yaml title="config.yaml" {6}
apiVersion: btp.sap.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: account-provider-config
spec:
  globalAccount: <global-account-subdomain>
  cliServerUrl: https://cli.btp.cloud.sap
  cisCredentials:
    source: Secret
    secretRef:
      name: cis-provider-secret
      namespace: default
      key: data
  serviceAccountSecret:
    source: Secret
    secretRef:
      name: sa-provider-secret
      namespace: default
      key: credentials
```

Replace `<global-account-subdomain>` with the subdomain of your BTP global account.
It must be the same global account whose subaccount holds the Cloud Management
service binding referenced in `cisCredentials`. Adjust `cliServerUrl` if your
landscape uses a different CLI server URL.

  </TabItem>
  <TabItem value="ias-oidc" label="IAS trusted OIDC">

Reference the same CIS binding Secret and configure the projected workload token.
Do **not** set `serviceAccountSecret`; workload mode rejects mixed password inputs.
The CIS binding must use `client_credentials`, as created in the shared setup.

```yaml title="config.yaml"
apiVersion: btp.sap.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: account-provider-config
spec:
  globalAccount: GA_SUBDOMAIN
  cliServerUrl: "https://cli.btp.cloud.sap"
  cisCredentials:
    source: Secret
    secretRef:
      namespace: default
      name: cis-provider-secret
      key: data
  workloadIdentity:
    tokenFile: /var/run/secrets/workload/token
    identityProvider: BTP_ORIGIN
    userEmail: WORKLOAD_EMAIL
```

Replace `GA_SUBDOMAIN` with the subdomain of the global account containing your
CIS binding. Adjust `cliServerUrl` if your landscape uses a different CLI server.
Use the exact `BTP_ORIGIN` and `WORKLOAD_EMAIL` from
the IAS/BTP setup. The `tokenFile` path must match the runtime mount from step 4.

This configuration needs only `tokenFile`, `identityProvider` and `userEmail`
under `workloadIdentity`. Keep the CIS binding Secret; no user password or IAS
client secret is added.


  </TabItem>
</Tabs>

Apply the configuration for your chosen approach:

```sh title="Run in Terminal"
kubectl apply -f config.yaml
```

## ⁉ FAQs

- **Do I need to restart the provider when changing the workload identity?** Yes—after
  changing the issuer, ServiceAccount subject, audience, or IAS/BTP identity mapping.
  Update IAS trust, BTP role assignments and `ProviderConfig` together before restarting.
  Normal token rotation for the same identity does **not** require a restart.
